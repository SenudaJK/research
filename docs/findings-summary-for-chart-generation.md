# Research Findings Summary — Autonomous Remediation for Cloud-Native Systems

**Purpose of this document:** A self-contained summary of quantitative results, methodological findings, and limitations from a chaos-engineering research project evaluating an ML-based anomaly detection + rule-based autonomous remediation pipeline against a manual/legacy baseline, on a Kubernetes deployment of the Online Boutique microservices demo. Intended as source material for generating charts and a narrative summary.

---

## 1. System Under Test

- **Target application:** Online Boutique (12-microservice demo app) on Kubernetes.
- **Fault injection:** Chaos Mesh (StressChaos, PodChaos, NetworkChaos, IOChaos, manual `kubectl patch` for config drift).
- **Detection model:** Isolation Forest anomaly detector trained on a 6-feature cluster-wide state vector (`cpu_util`, `mem_util`, `network_rx`, `log_error_rate`, `trace_latency_ms`, `trace_error_pct`), threshold τ set at the 95th percentile of training scores.
- **Remediation:** A playbook of rules (`decision-engine/playbook.yaml`) mapping a triggering feature + z-score threshold to a Kubernetes-level action (`scale`, `restart`, `evict`, `reconcile`) executed by a custom Kubernetes operator via a `RemediationAction` CRD.
- **Two experimental conditions per scenario:**
  - **Run A (Legacy):** native Kubernetes self-healing only (readiness probes, restart policies, no ML/operator involvement).
  - **Run B (Proposed):** the full detect → match rule → act closed loop.
- **Metrics:** MTTD (Mean Time to Detect), MTTR (Mean Time to Recovery), Availability (span-count-based success ratio over the fault window), Detection outcome (TP/FP/FN/TN).

**Key takeaway for charts:** the system's core, well-supported result is still a **detection-speed** win (MTTD), not a recovery-speed win (MTTR) — MTTR is roughly flat between conditions across scenarios, and in several scenarios (S4, S7, S12's Run A) Run B's or Run A's *mean* MTTR is higher than its counterpart, driven by high variance (see §4 limitations) rather than a real, direction-consistent effect. The MTTD win itself is now visibly uneven across scenarios too, not a uniform 20x-plus speedup: S6 barely detects at all (1/5 trials), and S10's near-parity between conditions turns out to be an artifact of a broken fault injection, not a real result (see below).

**S3 is the sharpest illustration of why MTTD/MTTR numbers alone can be misleading (see §3.2 below): its Run B numbers look like a strong result in the table** (MTTD 36.49s, MTTR 66.61s, one of the lowest MTTR std devs of any scenario, 0.42) **— but the remediation action never once fired against the actually-faulted service across all 10 Run B trials.** The apparent "clean win" is an artifact of a different rule (`R2-pod-kill-restart` or `R1-cpu-starvation-scale`) reliably firing and the SLO never being meaningfully broken in the first place, not evidence the system correctly diagnosed and fixed this fault type. Do not present S3's numbers without this caveat directly alongside them.

**S10 is now the second, and more severe, instance of this same "don't trust a clean-looking number" pattern — its data is suspicious enough that it should not be presented as a positive result at all.** S10's Run A and Run B mean MTTD are nearly identical (24.25s vs 26.94s) — unlike every other scenario, where Run B's ML detection beats Run A's native signal by 10-50x — and both conditions show a suspiciously tight, near-zero-variance 100% success rate. Investigated against the raw trial JSON (`evaluation/runs/trials/scenario-10-http-5xx-*.json`): `trace_error_pct` is exactly `0.0` in every sample of every one of the 10 S10 trials, in both conditions, and `frontend_success_rate` never drops from 1.0. Root cause: `evaluation/scenarios/scenario-10-http-5xx.yaml`'s HTTPChaos spec sets `target: Request` while trying to `replace.code: 500` — that replacement only takes effect on a `target: Response` patch, so the fault most likely never actually injected a single real 500 response the entire campaign. Both conditions' "detection" almost certainly key off the same generic `log_error_rate` Chaos-Mesh-injection side effect documented since 2026-09-07, not off any HTTP-5xx-specific signal. **This data was kept in the CSV (it is not Jaeger-restart-contaminated, `trial_valid` is legitimately true) but must be read as evidence the fault injection is broken, not that either condition handles S10 well.** Not fixed here (a scenario-YAML/fault-injection change requires its own re-validation trial, out of scope for this analysis pass).

## 3. Qualitative / Architectural Findings

1. **Detection generalizes well; recovery-action correctness does not, by default.** The Isolation Forest + fixed τ reliably detects all five validated fault types (S1, S2, S3, S4, S7) with consistent ~6-45s MTTD. But *which* rule fires, and whether it targets the right service, is far less reliable — see the rule-collision findings below.

2. **Single-feature, largest-magnitude rule matching is a structural bottleneck, not a tuning problem.** Two independent failure mechanisms were found and diagnosed in production trials:
   - **Signal dilution (S2 / R3-memory-leak-restart):** the aggregate `mem_util` feature sums memory across all 12 services. A single service's (cartservice, 256Mi limit) leak is a small fraction of the ~2.1–2.4 GiB cluster-wide baseline, and gets OOMKilled faster than the 60s sample cadence can catch a sustained elevated reading. Result: `mem_util` never carries a usable signal for this fault, at *any* threshold. The system still "recovers" S2, but via `R2-pod-kill-restart` (triggered by `log_error_rate`) restarting **frontend**, not cartservice — a coincidental side effect, not a fix to the underlying leak.
   - **Rule collision (S9 vs. S11 / R5 vs. R6):** `network_rx` *does* carry a real, valid signal for S11 (DB pool exhaustion), but `trace_error_pct` (R5's trigger, intended for S9) reliably outmagnitudes it whenever both are elevated simultaneously — which they are, because S11's bandwidth throttle also raises request error rates via timeouts. The rule-matcher's "largest |z|-score wins" tie-break therefore always picks the wrong rule (R5, restarting redis-cart) even though R6's own signal, in isolation, is valid. This produced a fully executed, completely ineffective remediation action, and the trial's real recovery was the fault's own 5-minute expiry — not the system, and the trial was correctly discarded as invalid evidence.

3. **The rule-matching failure is now confirmed, not predicted, for every one of the six scenarios added on 2026-09-15 (S3, S5, S6, S8, S10, S12): the scenario's own intended rule fired zero times in every single case.** Tally across all real Run B trials collected: R7 (S3) 0/10, R8 (S5) 0/9, R9 (S6) 0/5, R10 (S8) 0/5, R11 (S10) 0/4, R12 (S12) 0/3 — **0/36 own-rule matches across six independently tested scenarios.** `R2-pod-kill-restart` alone accounts for the majority of these trials' outcomes (24/36, ~67%), with the remainder split across R1, R4, and R5 firing instead of the intended rule. **`log_error_rate` appears to spike as a near-universal side effect of Chaos Mesh fault injection regardless of the actual fault type** (first suspected in an S1 trial as early as 2026-09-07, now confirmed recurring across S3, S5, S6, S8, S10, and S12). Because `R2` sits early in `playbook.yaml`'s rule list, it wins not only real magnitude contests but also exact ties against rules sharing its identical trigger feature (e.g. `R9-dns-failure-restart`, which as a result is not merely *likely* to collide but **structurally unable to ever win** while both qualify, since Python's stable sort preserves list order on a tie). This reframes `R2-pod-kill-restart` from "the correct rule for S7" to "the model's de facto default output whenever anything crosses tau" — a materially different and more serious framing for the dissertation's limitations section than "occasional collision." At this point the finding is not "rule collision happens sometimes" but "under the current single-feature-magnitude matcher, a newly added rule has never once won a real trial against R1/R2/R4."
4. **A per-service-feature model (v2) was designed specifically to address (3), and is architecturally implemented but not yet evidence.** `decision-engine/model-config-v2.yaml` (10 features: the original 6 cluster-wide + 4 new per-service ones, most recently `cpu_util_paymentservice` added to fix R7/S3) and `decision-engine/playbook-v2.yaml` (corrected `trigger_feature`s for R3/R5/R6/R7) exist and pass synthetic-input verification, but have **not yet been validated against a real trained model + live cluster trial** — this is the single largest open item (see §5). Note v2 as designed would not fix S6 or S10/S12 (see findings 9-10 below) — it only re-targets the rule-matcher's *feature choice*, not the two newly found problems where the detector doesn't fire at all (S6) or the fault's own feature never carries any signal in any trial (S10/S12).

5. **Sampling-cadence artifacts can make MTTR look identical across conditions even when the mechanism is completely different.** For S1, S3, and S7 in particular, several trials showed near-identical MTTR between Run A and Run B not because the operator's action was equivalent in effect to native self-healing, but because (a) the SLO (`frontend_success_rate`) never meaningfully dropped in the first place (S1's CPU stress hurt backend latency without translating to frontend errors at this load level; S3's disk-io fault behaved the same way), or (b) a Deployment-managed pod-kill (S7) self-heals via Kubernetes' own pod replacement well inside the 60s sample cadence, in *either* condition. This is flagged explicitly in the experiment log as a measurement-protocol blind spot, not a code bug — some fault types at this scale/load are simply not good tests of the RQ3 "does autonomous remediation shorten recovery" claim.

6. **Infrastructure-level chaos-injection failures are a real, separate source of invalid data**, and recur across scenarios, not just once. An S9 (volume detachment) trial failed at the Chaos Mesh IOChaos layer itself (`toda`, the fuse-based fault injector, never successfully injected — `injectedCount: 0`), and got stuck retrying its own teardown, requiring a manual Kubernetes finalizer removal to unblock. An S10 (HTTP 5xx) trial hit the same failure class from a different trigger (a containerd-level race — `"no running task found"` — during injection), and because the measurement harness had no check for whether a "fresh" fault actually re-applied, this one cascaded into **8 consecutive trials silently measuring against one dead, un-cleaned-up resource** before the pattern (steadily climbing MTTD, a clock-drift artifact) was noticed; all 8 were discarded. This is orthogonal to the detection/remediation pipeline being evaluated, but consumed real experiment time and is now understood to be a recurring risk category, not a one-off.

7. **Three real software bugs in the measurement harness itself were found and fixed mid-campaign**, all of which would otherwise have silently corrupted trial data as false negatives or false "successes":
   - An unbounded API call (`create_namespaced_custom_object` with no request timeout) could stall an entire trial's remaining time budget on a transient apiserver hiccup, producing a false-censored (`MTTD=600s`) result indistinguishable from a genuine detection failure. Fixed with a 15s request timeout + retry.
   - Rule-matching originally considered only the single most-deviated feature at the *first* anomalous sample and never retried on subsequent samples — meaning a real, strongly-triggering feature (e.g., `cpu_util` z=22) could be permanently missed because a coincidental, rule-less feature (`log_error_rate`) was marginally larger on the very first anomalous tick.
   - Every `kubectl`/shell call in the trial harness had no execution timeout at all — a single stuck Chaos Mesh cleanup could (and did, for S10) hang a trial for hours, and a subsequent trial could silently trust a stale, never-actually-refreshed fault's timestamp as if it were fresh. Fixed with a bounded timeout on every shell call, a self-healing finalizer-clear step when cleanup doesn't complete, and a hard failure if the fault never demonstrably went active, rather than continuing on unverified state.

8. **Sample sizes are uneven and, for the six most-recently-added scenarios, quite small** (S4: 10A/7B, S7: 10A/7B — 3 more of each still needed per the experiment log; S1 is well-powered at 32A/27B; S2 sits at 12A/10B; S3 is well-powered at 10A/10B; but S5 sits at 10A/9B, S6 at 4A/5B, S8 at 4A/5B, S10 at 5A/4B, and S12 at just 4A/3B). This should be disclosed as a limitation on statistical confidence, particularly for the higher-variance MTTR numbers — the smallest cells (S6/S8/S10/S12) are 3-5 trials, not the N=10 target.

9. **S6 (DNS failure) shows a raw detection failure, a third and distinct failure mode from signal dilution and rule collision.** Only 1 of 5 real Run B trials detected the fault at all (`anomaly_score` crossing τ); the other 4/5 ran the full 600s window with no detection (`td_censored`). Unlike S3/S5/S8/S10/S12, where the detector fires correctly and only the *rule match* targets the wrong service, S6's fault barely perturbs any of the 6 v1 features enough to cross τ in the first place. This is a detection-recall gap, not a remediation-targeting gap — the v2 per-service model, which only adds new targeting features, would not be expected to fix it.

10. **S10 (HTTP 5xx) and S12 (config drift) show a fourth, even more fundamental failure mode: the rule's own trigger feature (`trace_error_pct`) never carries any signal at all, in any trial, in either condition.** `trace_error_pct` is exactly `0.0` in every sample of every S10 trial (10/10) and every S12 trial (8/8) — contrast with the S2/S9-vs-S11 findings above, where the relevant feature carried a real but diluted/out-competed signal. Here there is no signal to dilute or lose a collision over. Root-caused for S10: `evaluation/scenarios/scenario-10-http-5xx.yaml`'s HTTPChaos spec sets `target: Request` while trying to `replace.code: 500` — that code-replacement only takes effect on a `target: Response` patch, so the fault most likely never injected a single real 500 response across the whole campaign. S10's near-identical Run A/Run B MTTD (24.25s vs 26.94s, unlike every other scenario's 10-50x gap) is consistent with both conditions merely picking up the same generic `log_error_rate` injection side-effect from finding 3, not any HTTP-5xx-specific signal — **S10's numbers should not be read as a positive result for either condition; they are evidence the fault injection itself is broken.** This was not fixed as part of this analysis pass (a scenario-YAML change needs its own re-validation trial) — it is the most concrete, actionable next step for S10.

11. **5 of the twelve fault scenarios (S5, S6, S8, S10, S12) now have real trial data, but every one of them confirms rather than resolves the project's structural findings.** Combined with S3, that is six of six newly-tested scenarios where the intended rule never fired — see finding 3. S9 (volume detachment) remains the only fault scenario in scope with zero valid trial data at all, blocked by the unresolved Chaos Mesh `toda` infrastructure issue (finding 6).

## 4. Limitations (for explicit disclosure in any write-up)

- **MTTR improvement is not established.** The global 4.74% MTTR reduction is small relative to its variance (std dev up to 82s per scenario/condition) and is not a clean, monotonic win across scenarios — S4, S7, and S12 (Run A) show mean MTTR *higher* in one condition than the RQ3 hypothesis would predict. This should not be reported as a positive result without heavy caveats — this conclusion has now held across every scenario batch collected, not softened by adding more data.
- **Several scenarios undershoot the target sample size, some severely**: S4/S7 sit at 7B (vs. 10 target); S6, S8, S10, S12 sit at 3-5 trials per condition. One scenario (S9) has zero valid trials at all due to an infrastructure fault-injection failure.
- **Six structural rule-matching/detection failure modes are now documented, only two of which have a design-level fix that itself remains unvalidated on real data**: signal dilution (S2, R3), rule collision under simultaneous qualification (S9/S11, R5/R6), rule collision confirmed live for S3 (R7, 0/10), and now the same live-confirmed collision for S5/S8/S12 (R8/R10/R12, each 0/N) — five rules whose only design-level fix (v2 per-service features) has zero real-cluster validation. Two further failure modes have **no proposed fix at all yet**: S6's raw detection-recall gap (detector doesn't fire 4/5 times) and S10/S12's dead-feature problem (`trace_error_pct` never nonzero — the fault injection itself appears broken for S10, per its `HTTPChaos target: Request` bug).
- **`R2-pod-kill-restart` functioning as a de facto catch-all rule, not a scenario-specific one, is now supported by data across all six independently tested new scenarios (S3, S5, S6, S8, S10, S12), not a handful of anecdotes** — the scenario's own intended rule has fired in precisely 0 of 36 real Run B trials across these six scenarios. This is now one of the project's central findings, not a caveat: under the current architecture, a newly designed remediation rule has never once won against R1/R2/R4 in a real trial.
- **All twelve fault scenarios in scope now have at least attempted trial data except S9** (still blocked by the unresolved Chaos Mesh `toda` infrastructure issue) — but "has data" does not mean "validates the system": every one of the six most-recently-run scenarios confirms a failure mode rather than a working remediation path.
- **The frozen v1 model is a single Isolation Forest trained once** (`20260906T023729Z`); no cross-validation across multiple independently trained models is reported, so some of the observed generalization could be specific to this one trained artifact.
- **Some MTTR parity between conditions is a measurement-protocol artifact** (60s sampling cadence too coarse to distinguish native self-healing from operator-driven remediation for fast-resolving faults), not necessarily evidence that the two conditions perform equivalently.
- **At least one scenario's fault injection (S10) is confirmed broken at the config level**, and this was only caught by scrutinizing a suspiciously clean result rather than by an upfront check — raising the question of whether other scenarios' fault injections were validated as actually landing (S1/S2/S3/S4/S7/S9/S11 all have direct evidence the fault was real via feature movement or documented infra failures; S6 and S12's weak/absent signal is at least consistent with, though not proof of, a similar injection problem, and was not root-caused with the same rigor as S10 in this pass).

## 5. Current Status / What's Left

- Bring S4-B, S7-B, S5, S6, S8, S10, S12 up toward N=10 per condition — most of the newest scenarios are currently at 3-5 trials, too few to trust the point estimates, though the *qualitative* finding (own rule never fires) is already unambiguous at these sample sizes (0/N with N≥3 across six scenarios is not a small-sample artifact).
- Collect a fresh ≥200-sample baseline, train, and run real S2/S3/S5/S8/S9/S11/S12 trials under the v2 per-service-feature model to test whether it actually resolves the signal-dilution and rule-collision failures (currently only synthetically verified on any of them). Note v2 is not expected to help S6 or S10 (see findings 9-10) — those need their own fixes first (S10: correct the HTTPChaos `target`/`replace` config; S6: root-cause which feature, if any, actually moves during DNS failure).
- Resolve the Chaos Mesh IOChaos/`toda` infrastructure issue blocking any valid S9 data — the only scenario in scope with zero data at all.
- Fix and re-run S10's fault injection (`target: Request` → `target: Response` in `evaluation/scenarios/scenario-10-http-5xx.yaml`) — the current 10 trials are not usable as evidence for this scenario.
- Investigate S6's detection-recall gap directly (why 4/5 trials never cross τ at all) before assuming any fix (v2 or otherwise) will help it.
- Determine whether `log_error_rate`'s apparent near-universal spike on fault injection is a real artifact of the test environment worth its own root-cause investigation, since it now explains the dominant failure mode across all six of the newest scenarios, not scenario-specific noise.

## 6. Self-Assessment / Rating (my opinion, for context — not a finding)

**Updated 2026-09-18, after S5/S6/S8/S10/S12 were analyzed.** The project has now reached a natural stopping point for *data collection*, though not because the system works — because the remaining open questions are no longer answerable by running more trials of the same kind.

This is a solid, credible piece of applied systems research at what reads like an MSc/early-PhD dissertation level, and the evidence base for its **failure-mode taxonomy** (RQ2-adjacent: what breaks and why) is now genuinely complete and strong: real cluster experiments across all 11 reachable fault scenarios (S9 excluded only by an unresolved infra bug, not skipped), honest documentation of every failure mode including ones that make the system look bad, several genuine measurement-bugs found and fixed rather than papered over, and — as of this pass — a clean, no-exceptions result that a newly designed remediation rule has fired 0 times in 36 real trials across six independently tested scenarios. That is not a preliminary signal anymore; it is a saturated, reproduced-six-times finding. Continuing to run more S5/S6/S8/S10/S12-style trials at this point would mostly tighten confidence intervals on numbers that already point one way, not change the conclusion.

The picture is much weaker on the paper's other two central claims. **RQ1 (detection speed)** is well-supported for the scenarios where the detector actually fires (S1-S5, S7, S8, S12 to varying degrees) but is now visibly *not* universal: S6 fails to detect in 4/5 trials, and S10's apparent detection is very likely a broken-fault-injection artifact rather than real signal. **RQ3 (recovery speed)** remains weak-to-null after 11 scenarios' worth of data (4.74% global MTTR reduction, not a clean or monotonic win, unchanged in direction since the very first S1/S2 trials) — more data has not moved this number toward significance, which is itself informative: this isn't a small-sample problem, it looks like a real property of the current architecture (detection fires and a *some* action is taken quickly, but that action is usually the wrong one, so it rarely actually shortens the outage).

**Recommendation on stopping:** yes, this is a reasonable point to stop new data collection and move to writing up, provided the thesis's own framing does the following honestly rather than presenting the system as more finished than it is:
1. Report RQ1 as a qualified win (strong for most scenarios, with S6/S10 as documented exceptions with their own root causes), not a universal one.
2. Report RQ3 as an explicitly negative/null result, backed by the observation that the null held steady across 11 scenarios and roughly 200 trials, not just a couple of noisy runs.
3. Present the six-scenario, zero-real-hits rule-collision finding as a primary contribution in its own right — a taxonomy of *why* single-feature-magnitude rule matching fails in production, which is a defensible and interesting result even though (especially because) it means the "autonomous remediation" system doesn't autonomously remediate most fault types correctly.
4. Explicitly flag the two loose ends that data collection cannot resolve without further engineering work first, not more trials: the v2 model's real-cluster validation (still zero evidence either way) and S10's broken fault injection — both should be listed as "future work," not quietly finished or quietly ignored.
5. Disclose sample-size limitations honestly per scenario (§4) — several of the newest scenarios are only at N=3-5, which is enough to support the qualitative rule-matching finding (0/N is 0/N) but not enough to put much weight on the exact MTTD/MTTR point estimates for those scenarios individually.

If time and cluster access allow one more round before writing begins, the highest-value use of it would be fixing S10's fault injection and getting a v2-model real trial (even just for S3, the most cleanly diagnosed case) — either result (v2 works / v2 doesn't work) is publishable and would upgrade "designed but unproven" to an actual finding. But this is optional polish, not a blocker: the thesis is defensible today with the negative/qualified results honestly framed, and chasing a positive RQ3 result by running more of the same trial types is unlikely to produce one given how stable the null has been.
